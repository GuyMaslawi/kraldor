# חנות היהלומים — סליקה דרך Grow עם Make

איך kraldor גובה כסף אמיתי דרך **Grow (משולם)** כשממשק ה־API הישיר של Grow סגור,
באמצעות תרחישים (scenarios) ב־**Make**.

## למה בכלל Make

ה־Light API של Grow (`createPaymentProcess`) הוא תוסף בתשלום שלא נרכש. בלעדיו כל
קריאה ישירה חוזרת עם:

```
{"status":0,"err":{"id":701,"message":"פרמטר קוד זיהוי אינו תקין: userId"}}
```

זו לא שגיאת תצורה ואי אפשר לתקן אותה בערך אחר — אין `userId` להזין. אפליקציית
Grow ב־Make מגיעה עם החיבור שלה ואינה דורשת את התוסף, ולכן היא הדרך פנימה.
אלורה כבר עובדת ככה בפרודקשן על **אותו חשבון סוחר**.

## התמונה הגדולה

```
שחקן לוחץ על חבילת יהלומים
        │
        ▼
kraldor פותח שורת רכישה PENDING ושולח ל-Webhook של Make (תרחיש 1)
        │
        ▼
Make קורא ל-Grow "Create Payment Link" ומחזיר { url, processId, processToken }
        │
        ▼
השחקן משלם בעמוד הסליקה של Grow
        │
        ├──────────────► Grow שולח callback ל-/api/pay/grow/<secret>
        └──────────────► הדפדפן חוזר ל-/game/diamonds/buy/success
                                    │
                    שניהם עושים את אותו דבר:
                                    ▼
              kraldor שואל את Make (תרחיש 2) כמה העסקה שווה
                                    ▼
                    רק התשובה הזו מזכה יהלומים
```

## הכלל שכל המסמך הזה משרת

**Grow לא חותם על ה־callbacks שלו.** `/api/pay/grow/<secret>` הוא נתיב ציבורי,
וגוף הבקשה שמגיע אליו לא מאמת דבר. מה שמגן על החנות הוא שהסכום **נקרא בחזרה
מ־Grow** ולעולם לא מתוך גוף ה־callback ([grow.ts](../src/server/grow.ts)).

לכן **תרחיש 2 אינו רשות.** בלעדיו כל מי שינחש את הכתובת מדפיס יהלומים בחינם.
זה ההבדל מאלורה, שבה ה־callback רק מאריך מנוי ואין מה לזייף.

## מה לבנות ב-Make

שלושה תרחישים **חדשים**. אל תיגע בתרחיש של אלורה — הוא מוגדר להוראת קבע, ומנוי
שעובד בפרודקשן הוא לא מקום להתנסות.

לכל תרחיש: `Webhooks › Custom webhook` → מודול Grow → `Webhooks › Webhook response`.
בכל אחד, הפעל **Scheduling: ON / Immediately** בסיום.

### תרחיש 1 — יצירת קישור תשלום

שם מוצע: `kraldor-create-payment-link` → הכתובת נכנסת ל־`MAKE_GROW_CREATE_LINK_WEBHOOK_URL`.

**מה kraldor שולח** — כותרת `x-make-apikey: <MAKE_WEBHOOK_API_KEY>`, וגוף JSON:

```json
{
  "sum": "1.00",
  "description": "400 יהלומים KRALDOR",
  "fullName": "גיא מוסלאוי",
  "phone": "0525756333",
  "email": "guy@example.com",
  "successUrl": "https://kraldor.com/game/diamonds/buy/success",
  "cancelUrl":  "https://kraldor.com/game/diamonds/buy/cancel",
  "notifyUrl":  "https://kraldor.com/api/pay/grow/<GROW_CALLBACK_SECRET>",
  "cField1": "<purchaseId>"
}
```

**מודול Grow › Create Payment Link** — השדות למטה הם השמות האמיתיים במודול,
נקראו מהמסך ולא מהתיעוד. מה שלא מופיע בטבלה — השאר ריק.

| שדה | ערך | למה |
| --- | --- | --- |
| Connection | `Allura Grow connection` | אותו חשבון סוחר; אל תיצור חיבור חדש |
| Sending Mode | **none** | אנחנו מפנים לקישור בעצמנו, בלי SMS |
| Full Name | `fullName` | Grow דוחה שם בעל מילה אחת |
| Phone | `phone` | |
| Email | `email` | |
| **Charge Type** | **Regular Charge** | לא `j4j5` — זו תפיסת מסגרת בלי גבייה, שמשאירה כל רכישה PENDING לנצח. ולא `Empty`: השדה אינו חובה, וריק נופל לברירת מחדל שאיש לא הצהיר עליה |
| success Url | `successUrl` | |
| **Invoice Notify Url** | **ריק** | לקבלות, לא לתשלומים. בלבול עם השדה הבא = אף תשלום לא מדווח |
| **notify Url** | `notifyUrl` | לשם מגיע חיווי התשלום. בלעדיו אין זיכוי |
| Title | `description` | כותרת קישור התשלום |
| **Transaction Type** | Credit Card · Bit · Apple Pay · Google Pay | **לא `Select All`** — הוא גורר `Bank Transfer`, שנסגרת ימים אחרי הלחיצה. יהלומים הם מוצר מיידי; אמצעי שאינו מיידי משאיר את השחקן PENDING בלי יהלומים |
| **Payment Type** | **Payments** | לא `Recurring Payment` — זו הוראת קבע, ומה שאלורה משתמשת בו. כאן היא תחייב שחקן כל חודש על יהלומים שקנה פעם אחת |
| **Max or Custom** | **Custom Payments** | ולא `Max Payments`: שדה המספר שלו מתחיל ב-2, כלומר אי אפשר לבטא בו תשלום בודד |
| **Payments Number** | **`1`** — מוקלד | תשלום אחד, בלי בורר תשלומים לשחקן |
| Custom Field 1 | `cField1` | מזהה שורת הרכישה שלנו, חוזר אלינו בחיווי |

**אין שדה Sum.** הסכום נכנס כשורת מוצר, ו־Products List הוא שדה חובה. **פריט אחד
בלבד:**

| שדה בפריט | ערך |
| --- | --- |
| Product Name | `description` |
| Price | `sum` |
| **Quantity** | **`1` — מספר קבוע שמקלידים, לא ממופה** |
| **VAT Type** | **VAT Exempt** |
| Catalog Number · Minimum Quantity · Product URL | ריקים |

`Quantity` קבוע כי `sum` הוא כבר הסכום הסופי של החבילה. כמות 2 תחייב את השחקן
כפול בעוד שורת הרכישה דורשת את המקורי — כלומר `mismatch`: שילם, ולא קיבל יהלומים.

**`VAT Type` = VAT Exempt כי המפעיל הוא עוסק פטור.** `Regular VAT` יוסיף שורת
מע״מ לכל קבלה, וזה מסמך מס שגוי בכל מכירה שצריך לפרק מול רשות המסים בדיעבד. זו
אותה החלטה שכבר התקבלה עבור אלורה — אותו עוסק.

**למה תשלום אחד ולא פריסה.** לא ידוע אם Grow מדווח בעסקת תשלומים את הסכום המלא
או את התשלום הראשון. אם זה השני, `captureOrder` יראה סכום נמוך מ-`priceIls`
ו-`settleDiamondPurchase` יסמן `mismatch` — השחקן חויב ולא קיבל יהלומים. על סכומים
של ₪19.90–₪279.90 פריסה ממילא חסרת היגיון, אז אין מה לשלם עבור הבירור הזה.

> **`cancelUrl` נשלח ואין לאן למפות אותו.** למודול אין שדה ביטול, רק `success Url`.
> קונה שנוטש את דף הסליקה לא יוחזר ל-`/game/diamonds/buy/cancel` שלנו. לא מזיק —
> שום שורה לא משתנה — אבל אל תחפש את השדה הזה, הוא לא קיים.

**Webhook response** — סטטוס `200`, כותרת `Content-Type: application/json`, וגוף
עם שלושת המפתחות האלה **בדיוק** (הקוד קורא לפיהם):

```json
{ "url": "…", "processId": "…", "processToken": "…" }
```

שמות הפלט אצל Grow הם `URL` / `Payment Link Process ID` / `Payment Link Process
Token`.

> ⚠️ **בחר את שלושת הערכים מחלון המיפוי, תחת הסקשן של Grow — אל תקליד מספר מודול.**
> מספרי המודולים אינם זהים בין תרחישים: בתרחיש של אלורה Grow הוא מודול 2, ואצלנו
> 2 הוא ה-Custom webhook. ערך שהוקלד כ-`{{2.data.url}}` ישלוף את הפלט של הווהבוק
> (שהשדות שלו הם `sum`/`description`/…), יחזיר מחרוזות ריקות, והקוד ידווח
> "חסרים url/processId/processToken". זו טעות שכבר קרתה פעם אחת בבנייה הזו.

### תרחיש 2 — אימות עסקה (הקריטי)

שם מוצע: `kraldor-get-payment-info` → `MAKE_GROW_PAYMENT_INFO_WEBHOOK_URL`.

**מה kraldor שולח** (עם אותה כותרת `x-make-apikey`):

```json
{ "processId": "…", "processToken": "…" }
```

**מודול Grow › Get Payment Link Info** — Connection: `Allura Grow connection`;
מפה `Payment link process ID` ו-`Payment link process token` מהווהבוק.

**מבנה הפלט — נקרא מריצה אמיתית על עסקה משולמת, לא מהתיעוד.** הוא מקונן בשתי
רמות של מערכים, ו-`cField1` יושב רמה אחת מעל השאר:

```
Data
└─ Payment link transactions[1]
   ├─ customField
   │  └─ Custom Field 1        ← cField1
   └─ transactions[1]
      ├─ Status Code: 2        ← statusCode   (Status: "שולם")
      ├─ Sum                   ← sum
      └─ Transaction ID        ← transactionId
```

**Webhook response** — סטטוס `200`, כותרת `Content-Type: application/json`, ארבעה
מפתחות בשמות האלה בדיוק:

```json
{ "statusCode": "…", "transactionId": "…", "sum": "…", "cField1": "…" }
```

> ⚠️ בחר כל ערך **מחלון המיפוי**, ואל תקליד נתיבים — הם מקוננים וארוכים. שים לב
> שיש בעץ שני שדות בשם `Payment Link Process ID` ועוד כמה שמות דומים; שלושת
> הראשונים נלקחים מתוך `transactions`, ו-`cField1` מתוך `customField`.

`Status Code: 2` הוא בדיוק מה ש-`PAID_STATUS_CODES` ב-[grow.ts](../src/server/grow.ts)
מכיר, ולכן אין צורך בשינוי קוד.

> **`transactions` הוא מערך, וזו מגבלה ידועה.** כרטיס שנדחה ואז הצליח עשוי לייצר
> יותר מאבר אחד, ואז `[1]` הוא הניסיון הכושל: `statusCode ≠ 2`, הרכישה נשארת
> PENDING ולא מזוכה. כלומר **נכשל סגור** — בטוח, אבל שחקן ששילם ומחכה. השורה
> נראית ב-`/admin/purchases`. אם זה יקרה בפועל, התיקון הוא לבחור מהמערך את האבר
> שסטטוסו 2 במקום את הראשון.

### תרחיש 3 — אישור קבלה (רשות)

שם מוצע: `kraldor-approve-transaction` → `MAKE_GROW_APPROVE_WEBHOOK_URL`.

**שולחים:** `{ "processId": "…", "transactionId": "…" }`
**מודול:** Grow › Approve Transaction. **תשובה:** `200`, הגוף לא נקרא.

בלעדיו Grow מנסה לשלוח את החיווי שוב שש פעמים בשעה. ה־webhook שלנו אידמפוטנטי
אז זה לא מזיק, רק רועש.

## משתני סביבה

```
MAKE_GROW_CREATE_LINK_WEBHOOK_URL=https://hook.eu2.make.com/xxxxxxxx
MAKE_GROW_PAYMENT_INFO_WEBHOOK_URL=https://hook.eu2.make.com/yyyyyyyy
MAKE_GROW_APPROVE_WEBHOOK_URL=                # רשות
MAKE_WEBHOOK_API_KEY=                         # רשות, מומלץ מאוד
GROW_CALLBACK_SECRET=<48 תווים, כבר קיים>
```

`GROW_USER_ID` ו־`GROW_PAGE_CODE` **יוצאים משימוש** — הם היו של ה־API הישיר.

**אימות מול Make** נעשה דרך `API Key authentication` בטופס יצירת הווהבוק, ולא
דרך שדה `secret` בגוף הבקשה כמו באלורה. Make אוכף אותו בקצה שלו, כך שבקשה זרה
נדחית **בלי לצרוך פעולה** מהתקרה החודשית — ובלי מודול Filter בתוך התרחיש. הגדר
את **אותו מפתח** בשלושת הווהבוקים; משתנה סביבה אחד מכסה את כולם.

שני הראשונים חייבים להיות מוגדרים יחד. תצורה חלקית משאירה את החנות על ספק הדמה
ומדווחת על עצמה ב־`purchaseBlockers()`, כדי שדיפלוי שהתכוון לגבות כסף ולא גובה
לא ייראה כמו דיפלוי שמעולם לא הוגדר.

## התקרה של Make — שווה לדעת מראש

התוכנית החינמית מוגבלת בפעולות לחודש (בסביבות 1,000 — תבדוק בתוכנית שלך). כל
רכישה צורכת פעולות משני תרחישים לפחות, **וזה אותו חשבון Make שאלורה רצה עליו**.

אם התקרה נגמרת באמצע החודש, שני המוצרים נופלים יחד: אצל אלורה מנוי חדש לא נפתח,
ואצל kraldor שחקן משלם ולא מקבל יהלומים. תדע את המספר לפני שהחנות נפתחת.

## העמוד הקבוע אינו בשימוש, והמיתוג הוא של אלורה

נבדק ב-12.8.2026 מול קישור תשלום אמיתי שנוצר דרך התרחיש. **העמוד הקבוע
"Kraldor diamonds" לא משתתף במסלול הזה כלל** — הוא נוצר עבור ה-API הישיר, שדרש
`pageCode`. מודול Make מייצר קישורים דרך החיבור שלו ואינו מקבל קוד עמוד, ולכן
הלוגו ותמונת האווירה שהועלו לאותו עמוד אינם מופיעים בשום מקום.

מה שכן מופיע בראש דף הסליקה הוא המיתוג **ברמת החשבון** — כלומר **"Allura"**,
עם אייקון חנות גנרי (לא הועלה לוגו ברמת החשבון).

**יש שתי שכבות מיתוג, וזה נבדק מול שני דפים אמיתיים:**

| שכבה | נקבע ב | בקישור חד־פעמי |
| --- | --- | --- |
| באנר, לוגו, כותרת | **העמוד הקבוע** | ❌ לא מופיע |
| שם העסק ("Allura") | **החשבון** | ✅ מופיע — וזה כל מה שמופיע |

העמוד הקבוע כן מציג את הבאנר, הקרסט והכותרת "Kraldor" — כלומר הנכסים תקינים
ומיתוג ברמת עמוד עובד. אבל **"Allura" מופיע גם שם**, מתחת ללוגו, כי הוא שם
העסק ברמת החשבון. ובקישור החד־פעמי אין אפילו את זה: רק "Allura" ואייקון חנות גנרי.

**זו בעיה אמיתית, לא קוסמטית.** קונה שמזין מספר כרטיס אשראי בדף שנושא שם של עסק
אחר הוא קונה שפותח chargeback.

**ההמלצה:** לשנות את שם העסק בחשבון לשם הישות המשפטית (הגדרות → פרטי עסק). עוסק
אחד, שם אחד, נכון לשני המוצרים. הפשרה: גם דף התשלום של אלורה יפסיק לומר "Allura".

**וחשוב לא פחות מהדף:** ה-descriptor שמופיע בפירוט כרטיס האשראי של הקונה. זה
הגורם מספר אחת ל-chargeback — הדף נראה לשנייה, השורה בחיוב נשארת חודש. לברר מול
Grow מהו ומה ניתן לשנות בו.

שורת המוצר מקלה אך אינה פותרת: ברכישה אמיתית היא תישא את המילה KRALDOR
(`400 יהלומים KRALDOR`).

**מה שכן אומת באותו קישור** (ואלה היו שלוש שאלות פתוחות):

- הסכום מופיע **נעול**, בלי שדה קלט — הגדרת "סכום פתוח" בעמוד אינה מגיעה לקונה,
  כי הסכום נשלח בבקשה.
- **מע"מ ₪0** — `VAT Exempt` עובד; הקבלה לא תישא מע"מ.
- **אין בורר תשלומים** — `Custom Payments = 1` תפס.

## סדר עלייה לאוויר

1. שלושת התרחישים ב־Make, פעילים.
2. משתני הסביבה ב־Vercel (`npm run vercel:env`) + דיפלוי.
3. הנחת אדמין 95% ב־`/admin/balance` → "ניצוץ" יורד ל־₪1.00.
4. רכישה אמיתית אחת בכרטיס שלך. לוודא: הסכום נעול בעמוד הסליקה · הכסף
   **בדשבורד של Grow** · שורה PAID ב־`/admin/purchases` · 400 יהלומים במאזן ·
   קבלה בלי שורת מע״מ (עוסק פטור).
5. להחזיר את ההנחה ל־`0`. **לפני** השלב הבא, לא אחריו.
6. `DIAMOND_PURCHASES_LIVE=true`.

האינטרלוקים ב־[`arePurchasesLive()`](../src/server/payments.ts) אוכפים את הסדר
הזה. הם לא אוכפים שבאמת הסתכלת בחשבון הבנק — וזו הבדיקה היחידה שקובעת: הסנדבוקס
של Grow כבר דיווח פעם על תשלום מוצלח לחלוטין עבור אלורה, בלי ששקל זז בשום מקום.
